# Выпуск новой версии

Этот документ описывает выпуск `repo-guard`, после которого потребители могут закрепиться за воспроизводимой версией.

## Версионирование

`repo-guard` использует [семантическое версионирование](https://semver.org/):

- **исправление** (`x.y.Z`) — исправления ошибок без изменения публичных интерфейсов;
- **минорная версия** (`x.Y.0`) — обратно совместимые возможности;
- **мажорная версия** (`X.0.0`) — несовместимые изменения `CLI`, схемы политики, входов действия или машинного результата.

Архитектурная разработка не создаёт выпуск автоматически. Номер в `package.json.version` может быть принят заранее как состояние пакета без опубликованного выпуска. Официальный выпуск начинается только с уже принятого точного коммита, содержащего выбранную версию; между этим коммитом и созданием тега нельзя менять код или номер версии.

## Инвариант выпуска

`package.json.version` точного принятого коммита `S` определяет ожидаемый официальный тег `v<version>`:

```text
package.json.version = X.Y.Z
Git tag/release       = vX.Y.Z
release commit        = exact accepted SHA S
```

Версия и тег не вводятся в процесс выпуска как независимые параметры. Единственный вход транзакции — полный 40-символьный `S`; версия читается из `package.json` этого коммита, а имя тега выводится из неё.

Само наличие номера в `package.json.version` не означает, что версия уже выпущена. Пока соответствующего опубликованного тега и выпуска нет, потребители должны использовать полный 40-символьный идентификатор принятого коммита.

Команда `repo-guard init` не выводит ссылку действия из версии автоматически. Для `--action-ref` требуется явно передать полный 40-символьный идентификатор коммита либо строгий тег `vX.Y.Z`, совпадающий с текущим `package.json.version`.

## Что означает атомарная транзакция

Выпуск выполняет `.github/workflows/release.yml` как одну транзакцию вокруг неизменяемого `S`:

```text
S
 -> read-only preflight(S)
 -> ensure tag(version) == S
 -> ensure published Release(tag)
 -> повторно проверить tag == S
 -> release-integrity
```

«Атомарная» здесь означает, что после начала операции цель выпуска не может переключиться с `S` на более новый `main`. Платформа не предоставляет общего механизма отката для уже выполненных операций с тегом и выпуском, поэтому рабочий процесс не утверждает механическую транзакционность внешнего программного интерфейса. Любое противоречие или гонка приводит к блокировке; существующий тег никогда не перемещается и не перезаписывается.

Рабочий процесс запускается через `repository_dispatch` из доверенной ветки по умолчанию. Это не позволяет выбирать произвольную ветку с изменённым процессом выпуска. Передаваемый `client_payload.sha` остаётся недоверенным входом и полностью проверяется заданием `preflight`.

## Предварительная приёмка

До выпуска `S` уже должен быть принят в `main` обычным процессом разработки и содержать окончательный `package.json.version`.

Для `S` должны быть успешны:

```text
post-merge CI: workflow=.github/workflows/ci.yml, event=push, branch=main, head_sha=S
Policy Observatory Pages: workflow=.github/workflows/pages.yml, event=workflow_run, head_sha=S
```

В задании `preflight`, имеющем только права чтения, дополнительно проверяются:

- рабочая копия имеет `HEAD == S`;
- текущий `main == S` на момент допуска;
- `package.json.version` и оба корневых отражения версии в `package-lock.json`;
- `npm run check:dist`;
- существующий тег: отсутствует либо указывает точно на `S`;
- существующий выпуск на платформе: отсутствует либо уже опубликован как обычный, не `draft` и не `prerelease`;
- наблюдение тега и выпуска выполняется через существующий `observeReleaseTruth()`.

Если после принятия `S` требуется изменение кода или версии, нужен новый обычный цикл PR и новый принятый SHA. Выпуск не переносится на новый `main` автоматически.

Между принятым `S` и созданием тега нет отдельного коммита версии и нет повторного `npm version`.

## Запуск выпуска

После успешной приёмки после слияния зафиксируйте полный `S` и отправьте событие выпуска:

```bash
S=<40-char-accepted-SHA>

gh api --method POST \
  repos/netkeep80/repo-guard/dispatches \
  -f event_type=release \
  -f "client_payload[sha]=$S"
```

Другие параметры версии или тега передавать не нужно.

Рабочий процесс состоит из двух заданий с разными полномочиями.

### `preflight`

`preflight` имеет только права чтения. Он получает точную рабочую копию `S`, выполняет проверки принятия и выдаёт следующему заданию только:

```text
sha
version
tag
```

Здесь допустимо выполнение `npm ci`, `check:dist` и кода репозитория только для чтения, поскольку полномочий записи нет.

### `publish`

`publish` запускается только после успешного `preflight` и имеет `contents: write`.

В этом задании запрещены получение рабочей копии репозитория, `npm`, `node`, обработчики установки, `uses: ./` и любое выполнение кода выпускаемого кандидата. Оно использует только программный интерфейс платформы и проверенные значения `sha`, `version`, `tag` из `preflight`.

Поведение идемпотентно:

- тег отсутствует — создаётся `refs/tags/<tag>` строго на `S`;
- тег уже разрешается в `S`, включая аннотированный тег — существующий тег сохраняется;
- тег разрешается в другой коммит — выпуск блокируется без принудительного перемещения или обновления;
- выпуск отсутствует — создаётся опубликованный обычный выпуск;
- корректный выпуск уже существует — повторный запуск не меняет его;
- `draft`, `prerelease` или иное противоречивое состояние — выпуск блокируется.

После публикации точный `refs/tags/<tag>` снова разрешается до коммита и сравнивается с `S`. Одноимённая ветка не считается доказательством существования тега.

## Финальная проверка

Объект выпуска, созданный заданием `publish` с помощью `GITHUB_TOKEN`, не используется как транспорт события между рабочими процессами: автоматическая проверка не полагается на появление отдельного события `release: published`.

`Release integrity` автоматически запускается через `workflow_run` после завершения `Atomic release`. В задании `preflight` с правами только на чтение заранее создаётся артефакт данных с точной идентичностью цели: `target_sha`, `tag`, исходные `run_id` и `run_attempt`. В артефакте находятся только данные уже доказанной цели выпуска; он не является новым журналом состояния и не содержит исполняемого кода.

До получения рабочей копии выпуска `Release integrity` проверяет доверенное происхождение исходного запуска и соответствие артефакта конкретным `run_id` и `run_attempt`. Затем автоматическая проверка получает рабочую копию строго `target_sha = S` и вызывает `verify-release-ref.mjs` с `--tag` и `--expected-sha`. Поэтому успешный автоматический запуск относится именно к установленным `S` и тегу, а не к произвольной ссылке рабочего процесса.

После установления точной цели автоматический рабочий процесс записывает доказательство, связанное с `S`, тегом, исходным запуском `Atomic release` и собственным запуском. Если проверка выпуска завершается ошибкой, доказательство может сохранить этот результат только для уже установленной идентичности. Ошибка до установления идентичности цели не приписывается какому-либо принятому SHA.

Ручной запуск `Release integrity` по одному тегу сохраняется как отдельная диагностическая проверка. Он получает рабочую копию выбранного тега и запускает `verify-release-ref.mjs` без `--expected-sha`; такой результат сам по себе не доказывает, что исторический принятый `S` был установлен заранее.

Для машинно-проверяемого контракта сохраняется точная формулировка:

```text
Ручной запуск по одному тегу не является доказательством того, что исторический accepted `S` был установлен заранее.
```

При необходимости ту же проверку по тегу можно повторить локально:

```bash
npm run verify:release-ref -- --tag vX.Y.Z
```

В рамках этой проверки #530 новые теги или объекты выпуска не создаются и существующий официальный выпуск не изменяется.

Успешный выпуск означает, что версия, точный тег, принятый `SHA` и опубликованный выпуск согласованы. Это не является утверждением, что платформа технически запрещает владельцу репозитория изменить тег после выпуска; обнаружение такого расхождения остаётся задачей проверок целостности и наблюдения.

## Публикация в npm

`npm publish` не является частью атомарной транзакции выпуска и не выполняется автоматически. Он остаётся отдельной необязательной операцией до появления подтверждённого требования потребителя к публикации в реестре `npm`.

Если публикация в `npm` выполняется отдельно, `prepublishOnly` сначала запускает ту же проверку официальной ссылки выпуска.

## Проверка пакетного артефакта

Локальная дымовая проверка устанавливаемого артефакта:

```bash
npm pack
TARBALL=$(ls repo-guard-*.tgz)
TMPDIR=$(mktemp -d)
npm install --prefix "$TMPDIR" "$PWD/$TARBALL"
"$TMPDIR/node_modules/.bin/repo-guard" --repo-root "$PWD"
```

Та же граница используется в CI: `smoke-pack` проверяет устанавливаемый пакетный артефакт, а не только исходное дерево репозитория.

## Закрепление версии у потребителей

Для опубликованной npm-версии потребитель может использовать конкретный номер:

```bash
npm install -g repo-guard@X.Y.Z
npx repo-guard@X.Y.Z
```

В `GitHub Actions` после официального выпуска используйте его конкретный тег:

```yaml
- uses: netkeep80/repo-guard@vX.Y.Z
```

До публикации выпуска используйте полный 40-символьный идентификатор принятого коммита. Не закрепляйте производственную проверку за изменяемой веткой `main` или псевдонимом `latest`, если требуется воспроизводимость.

## Несовместимые переходы

Несовместимый архитектурный переход оформляется новой мажорной версией после его принятия. Старые команды, поля схемы, входы действия или режимы не сохраняются только ради совместимости, если действующая архитектурная спецификация требует их удаления. Исторические миграционные механизмы не являются частью процесса выпуска текущего ядра.

# Выпуск новой версии

Этот документ описывает выпуск `repo-guard`, после которого потребители могут закрепиться за воспроизводимой версией.

## Версионирование

`repo-guard` использует [семантическое версионирование](https://semver.org/):

- **исправление** (`x.y.Z`) — исправления ошибок без изменения публичных интерфейсов;
- **минорная версия** (`x.Y.0`) — обратно совместимые возможности;
- **мажорная версия** (`X.0.0`) — несовместимые изменения `CLI`, схемы политики, входов действия или машинного результата.

Архитектурная разработка не создаёт выпуск автоматически. Номер в `package.json.version` может быть принят заранее как состояние пакета без опубликованного выпуска. Официальный выпуск начинается только с уже принятого точного коммита, содержащего выбранную версию; между этим коммитом и созданием тега нельзя менять код или номер версии.

## Инвариант выпуска

`package.json.version` точного принятого коммита `S` определяет ожидаемый официальный тег `v<version>`:

```text
package.json.version = X.Y.Z
Git tag/release       = vX.Y.Z
release commit        = exact accepted SHA S
```

Версия и тег не вводятся в процесс выпуска как независимые параметры. Единственный вход транзакции — полный 40-символьный `S`; версия читается из `package.json` этого коммита, а имя тега выводится из неё.

Само наличие номера в `package.json.version` не означает, что версия уже выпущена. Пока соответствующего опубликованного тега и выпуска нет, потребители должны использовать полный 40-символьный идентификатор принятого коммита.

Команда `repo-guard init` не выводит ссылку действия из версии автоматически. Для `--action-ref` требуется явно передать полный 40-символьный идентификатор коммита либо строгий тег `vX.Y.Z`, совпадающий с текущим `package.json.version`.

## Что означает атомарная транзакция

Выпуск выполняет `.github/workflows/release.yml` как одну транзакцию вокруг неизменяемого `S`:

```text
S
 -> read-only preflight(S)
 -> ensure tag(version) == S
 -> ensure published Release(tag)
 -> повторно проверить tag == S
 -> release-integrity
```

«Атомарная» здесь означает, что после начала операции цель выпуска не может переключиться с `S` на более новый `main`. GitHub не предоставляет общего rollback для уже выполненных операций tag/Release, поэтому workflow не утверждает механическую транзакционность внешнего API. Любое противоречие или гонка обнаруживается fail-closed; существующий тег никогда не перемещается и не перезаписывается.

Workflow запускается через `repository_dispatch` из доверенной default branch. Это не позволяет выбирать произвольную ветку с изменённым release workflow. Передаваемый `client_payload.sha` остаётся недоверенным входом и полностью проверяется `preflight`.

## Предварительная приёмка

До выпуска `S` уже должен быть принят в `main` обычным процессом разработки и содержать окончательный `package.json.version`.

Для `S` должны быть успешны:

```text
post-merge CI: workflow=.github/workflows/ci.yml, event=push, branch=main, head_sha=S
Policy Observatory Pages: workflow=.github/workflows/pages.yml, event=workflow_run, head_sha=S
```

Внутри read-only `preflight` дополнительно проверяются:

- checkout `HEAD == S`;
- текущий `main == S` на момент допуска;
- `package.json.version` и оба корневых отражения версии в `package-lock.json`;
- `npm run check:dist`;
- существующий тег: отсутствует либо указывает точно на `S`;
- существующий GitHub Release: отсутствует либо уже опубликован как обычный, не `draft` и не `prerelease`;
- наблюдение тега и Release выполняется через существующий `observeReleaseTruth()`.

Если после принятия `S` требуется изменение кода или версии, нужен новый обычный цикл PR и новый принятый SHA. Выпуск не переносится на новый `main` автоматически.

Между принятым `S` и созданием тега нет отдельного коммита версии и нет повторного `npm version`.

## Запуск выпуска

После успешной post-merge приёмки зафиксируйте полный `S` и отправьте событие выпуска:

```bash
S=<40-char-accepted-SHA>

gh api --method POST \
  repos/netkeep80/repo-guard/dispatches \
  -f event_type=release \
  -f "client_payload[sha]=$S"
```

Другие параметры версии или тега передавать не нужно.

Workflow состоит из двух заданий с разными полномочиями.

### `preflight`

`preflight` имеет только права чтения. Он checkout'ит exact `S`, выполняет проверки принятия и выдаёт следующему заданию только:

```text
sha
version
tag
```

Здесь допустимо выполнение `npm ci`, `check:dist` и read-only кода репозитория, потому что write-credentials отсутствуют.

### `publish`

`publish` запускается только после успешного `preflight` и имеет `contents: write`.

В этом задании запрещены checkout репозитория, `npm`, `node`, install hooks, `uses: ./` и любое выполнение кода release candidate. Оно использует только GitHub API и проверенные значения `sha`, `version`, `tag` из `preflight`.

Поведение идемпотентно:

- тег отсутствует — создаётся `refs/tags/<tag>` строго на `S`;
- тег уже разрешается в `S`, включая annotated tag — существующий тег сохраняется;
- тег разрешается в другой commit — выпуск блокируется без force/update;
- Release отсутствует — создаётся опубликованный обычный Release;
- корректный Release уже существует — повторный запуск не меняет его;
- `draft`, `prerelease` или иное противоречивое состояние — выпуск блокируется.

После публикации точный `refs/tags/<tag>` снова разрешается до commit и сравнивается с `S`. Одноимённая ветка не считается доказательством существования тега.

## Финальная проверка

Публикация GitHub Release автоматически запускает `.github/workflows/release-integrity.yml`. Этот workflow остаётся независимой read-only проверкой и вызывает существующий `verify-release-ref.mjs`.

При необходимости ту же проверку можно повторить локально:

```bash
npm run verify:release-ref -- --tag vX.Y.Z
```

Успешный выпуск означает, что версия, точный тег, принятый SHA и опубликованный Release согласованы. Это не является утверждением, что GitHub технически запрещает владельцу репозитория изменить тег после выпуска; обнаружение такого расхождения остаётся задачей проверок целостности и наблюдения.

## Публикация в npm

`npm publish` не является частью атомарной GitHub release-транзакции и не выполняется автоматически. Он остаётся отдельной необязательной операцией до появления подтверждённого требования потребителя к npm-публикации.

Если npm-публикация выполняется отдельно, `prepublishOnly` сначала запускает ту же проверку официальной release-ссылки.

## Проверка пакетного артефакта

Локальная дымовая проверка устанавливаемого артефакта:

```bash
npm pack
TARBALL=$(ls repo-guard-*.tgz)
TMPDIR=$(mktemp -d)
npm install --prefix "$TMPDIR" "$PWD/$TARBALL"
"$TMPDIR/node_modules/.bin/repo-guard" --repo-root "$PWD"
```

Та же граница используется в CI: `smoke-pack` проверяет устанавливаемый пакетный артефакт, а не только исходное дерево репозитория.

## Закрепление версии у потребителей

Для опубликованной npm-версии потребитель может использовать конкретный номер:

```bash
npm install -g repo-guard@X.Y.Z
npx repo-guard@X.Y.Z
```

В `GitHub Actions` после официального выпуска используйте его конкретный тег:

```yaml
- uses: netkeep80/repo-guard@vX.Y.Z
```

До публикации выпуска используйте полный 40-символьный идентификатор принятого коммита. Не закрепляйте производственную проверку за изменяемой веткой `main` или псевдонимом `latest`, если требуется воспроизводимость.

## Несовместимые переходы

Несовместимый архитектурный переход оформляется новой мажорной версией после его принятия. Старые команды, поля схемы, входы действия или режимы не сохраняются только ради совместимости, если действующая архитектурная спецификация требует их удаления. Исторические миграционные механизмы не являются частью процесса выпуска текущего ядра.

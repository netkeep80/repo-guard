# Выпуск новой версии

Этот документ описывает выпуск `repo-guard`, после которого потребители могут закрепиться за воспроизводимой версией.

## Версионирование

`repo-guard` использует [семантическое версионирование](https://semver.org/):

- **исправление** (`x.y.Z`) — исправления ошибок без изменения публичных интерфейсов;
- **минорная версия** (`x.Y.0`) — обратно совместимые возможности;
- **мажорная версия** (`X.0.0`) — несовместимые изменения `CLI`, схемы политики, входов действия или машинного результата.

Архитектурная разработка не создаёт выпуск автоматически. Номер в `package.json.version` может быть принят заранее как состояние пакета без опубликованного выпуска. Официальный выпуск начинается только с уже принятого точного коммита, содержащего выбранную версию; между этим коммитом и созданием тега нельзя менять код или номер версии.

## Инвариант выпуска

`package.json.version` определяет ожидаемый официальный тег `v<version>`. Публикуемый пакет считается согласованным только тогда, когда соответствующие тег `Git` и выпуск на `GitHub` уже существуют и тег указывает на точный принятый коммит:

```text
package.json.version = X.Y.Z
Git tag/release       = vX.Y.Z
release commit        = exact accepted SHA
```

Само наличие номера в `package.json.version` не означает, что версия уже выпущена. Пока соответствующего опубликованного тега и выпуска нет, состояние остаётся непубликованным, а потребители должны использовать полный 40-символьный идентификатор принятого коммита.

Команда `repo-guard init` не выводит ссылку действия из версии автоматически. Для `--action-ref` требуется явно передать полный 40-символьный идентификатор коммита либо строгий тег `vX.Y.Z`, совпадающий с текущим `package.json.version`.

После создания официального тега и публикации выпуска проверьте инвариант:

```bash
npm run verify:release-ref -- --tag vX.Y.Z
```

`npm publish` запускает ту же проверку через `prepublishOnly`. Рабочий процесс проверки целостности выпуска повторяет её при публикации выпуска на GitHub.

## Предварительная приёмка

До создания официального тега точный кандидат уже должен содержать окончательный `package.json.version` и пройти проверки:

```text
npm run check:dist
npm test
npm run compression:metrics
validate = GREEN
smoke-pack = GREEN
```

Для изменения, проходящего через PR, сначала принимается точный идентификатор вершины (`head`) с обязательными проверками, затем проверяется точный идентификатор слияния (`merge SHA`) в `main`. Коммит выпуска не должен использоваться для обхода обычной проверки политики.

После этой приёмки выбранный коммит является неизменяемым кандидатом выпуска. Изменение кода или версии требует нового обычного цикла PR и новой приёмки; существующий кандидат больше нельзя тегировать как тот же самый принятый выпуск.

## Последовательность выпуска

1. Выберите точный принятый коммит `S` в `main`, который уже содержит окончательный `package.json.version = X.Y.Z`, и убедитесь, что обязательные проверки этого состояния завершились успешно.
2. Убедитесь, что после принятия `S` не требуется ни одного изменения кода или версии. Для проверки и последующего тега используйте полный 40-символьный идентификатор `S`.
3. Создайте неизменяемый тег `vX.Y.Z` именно на `S` и отправьте только этот тег:

   ```bash
   git tag vX.Y.Z <40-char-SHA>
   git push origin vX.Y.Z
   ```

4. Создайте и опубликуйте выпуск GitHub из того же тега `vX.Y.Z`.
5. Проверьте полную связь версии, тега, точного коммита и опубликованного выпуска:

   ```bash
   npm run verify:release-ref -- --tag vX.Y.Z
   ```

6. Только после успешной проверки опубликуйте пакет:

   ```bash
   npm publish
   ```

Между принятым `S` и созданием тега нет отдельного коммита версии и нет повторного `npm version`. Поле `files` в `package.json` определяет содержимое публикуемого пакета.

## Проверка опубликованного пакета

После публикации можно повторить локальную дымовую проверку:

```bash
npm pack
TARBALL=$(ls repo-guard-*.tgz)
TMPDIR=$(mktemp -d)
npm install --prefix "$TMPDIR" "$PWD/$TARBALL"
"$TMPDIR/node_modules/.bin/repo-guard" --repo-root "$PWD"
```

Та же граница используется в CI: `smoke-pack` проверяет устанавливаемый пакетный артефакт, а не только исходное дерево репозитория.

## Закрепление версии у потребителей

Для опубликованной версии потребитель должен использовать конкретный номер:

```bash
npm install -g repo-guard@X.Y.Z
npx repo-guard@X.Y.Z
```

В `GitHub Actions` используйте официальный неизменяемый тег выпуска после его публикации:

```yaml
- uses: netkeep80/repo-guard@vX.Y.Z
```

До публикации выпуска используйте полный 40-символьный идентификатор принятого коммита. Не закрепляйте производственную проверку за изменяемой веткой `main` или псевдонимом `latest`, если требуется воспроизводимость.

## Несовместимые переходы

Несовместимый архитектурный переход оформляется новой мажорной версией после его принятия. Старые команды, поля схемы, входы действия или режимы не сохраняются только ради совместимости, если действующая архитектурная спецификация требует их удаления. Исторические миграционные механизмы не являются частью процесса выпуска текущего ядра.

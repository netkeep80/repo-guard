# Выпуск новой версии

Этот документ описывает выпуск `repo-guard`, после которого потребители могут закрепиться за воспроизводимой версией.

## Версионирование

`repo-guard` использует [семантическое версионирование](https://semver.org/):

- **исправление** (`x.y.Z`) — исправления ошибок без изменения публичных интерфейсов;
- **минорная версия** (`x.Y.0`) — обратно совместимые возможности;
- **мажорная версия** (`X.0.0`) — несовместимые изменения CLI, схемы политики, Action-входов или машинного результата.

Архитектурная разработка не создаёт выпуск автоматически. Изменение `package.json.version`, тег и публикация выполняются отдельной release-границей после принятия соответствующего состояния `main`.

## Инвариант выпуска

`package.json.version` определяет ожидаемый официальный тег `v<version>`. Публикуемый пакет считается согласованным только тогда, когда соответствующие тег Git и выпуск на GitHub уже существуют:

```text
package.json.version = X.Y.Z
Git tag/release       = vX.Y.Z
```

Команда `repo-guard init` не выводит ссылку действия из версии автоматически. Для `--action-ref` требуется явно передать полный 40-символьный идентификатор коммита либо строгий тег `vX.Y.Z`, совпадающий с текущим `package.json.version`. До появления официального выпуска следует использовать идентификатор принятого коммита.

Для официального тега до публикации проверьте инвариант:

```bash
npm run verify:release-ref -- --tag vX.Y.Z
```

`npm publish` запускает ту же проверку через `prepublishOnly`. Рабочий процесс проверки целостности выпуска повторяет её при публикации выпуска на GitHub.

## Предварительная приёмка

Перед изменением версии должны быть выполнены проверки точного принимаемого состояния:

```text
npm run check:dist
npm test
npm run compression:metrics
validate = GREEN
smoke-pack = GREEN
```

Для изменения, проходящего через PR, сначала принимается точный head с обязательными проверками, затем проверяется точный merge SHA в `main`. Release-коммит не должен использоваться для обхода обычной проверки политики.

## Последовательность выпуска

1. Убедитесь, что `main` содержит именно принятое состояние и обязательные проверки завершились успешно.
2. Выберите уровень версии по фактическому изменению публичного контракта.
3. Обновите версию:

   ```bash
   npm version patch
   # либо minor / major
   ```

4. Повторите локальные и CI-проверки уже на коммите версии.
5. Отправьте коммит и тег:

   ```bash
   git push origin main --follow-tags
   ```

6. Создайте и опубликуйте выпуск GitHub из отправленного тега.
7. Повторно проверьте ссылку выпуска:

   ```bash
   npm run verify:release-ref -- --tag vX.Y.Z
   ```

8. Опубликуйте пакет:

   ```bash
   npm publish
   ```

Поле `files` в `package.json` определяет содержимое публикуемого пакета.

## Проверка опубликованного пакета

После публикации можно повторить локальную дымовую проверку:

```bash
npm pack
TARBALL=$(ls repo-guard-*.tgz)
TMPDIR=$(mktemp -d)
npm install --prefix "$TMPDIR" "$PWD/$TARBALL"
"$TMPDIR/node_modules/.bin/repo-guard" --repo-root "$PWD"
```

Та же граница используется в CI: `smoke-pack` проверяет устанавливаемый пакетный артефакт, а не только исходное дерево репозитория.

## Закрепление версии у потребителей

Для опубликованной версии потребитель должен использовать конкретный номер:

```bash
npm install -g repo-guard@X.Y.Z
npx repo-guard@X.Y.Z
```

В GitHub Actions используйте официальный неизменяемый тег выпуска после его публикации:

```yaml
- uses: netkeep80/repo-guard@vX.Y.Z
```

До публикации выпуска используйте полный 40-символьный идентификатор принятого коммита. Не закрепляйте производственную проверку за изменяемой веткой `main` или псевдонимом `latest`, если требуется воспроизводимость.

## Несовместимые переходы

Несовместимый архитектурный переход оформляется новой мажорной версией после его принятия. Старые команды, поля схемы, Action-входы или режимы не сохраняются только ради совместимости, если действующая архитектурная спецификация требует их удаления. Исторические миграционные механизмы не являются частью release-процесса текущего ядра.

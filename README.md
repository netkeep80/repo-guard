# repo-guard — границы изменения, свобода реализации

Человек определяет требования, полномочия и момент принятия результата. ИИ свободно выбирает реализацию внутри этих границ. `repo-guard` независимо проверяет объявленные ограничения изменения и связь утверждений с наблюдаемыми свидетельствами, не позволяя предложению изменения самому стать разрешением изменить правила.

Это небольшой проверяющий контур для репозитория. Он не планирует работу агента, не доказывает предметную корректность программы и не заменяет тесты, ревью или настройки защиты ветки.

## Полномочия человека и свобода ИИ

`ChangeIntent` описывает намерение PR. `GovernanceGrant` — отдельную доверенную санкцию из тела связанной задачи. Намерение не является санкцией. Проверка использует политику доверенной базовой ветки; изменение правил требует разрешения, полученного за пределами самого PR.

Наличие успешного действия ещё не запрещает обход через слияние или прямую запись. Для действующей границы нужны обязательная проверка от доверенного производителя, защищённая ветка и разделение прав предлагающего изменение и разрешающего его. Начальная конфигурация эти настройки платформы не устанавливает.

[Требования продукта](docs/product-requirements.md) определяют гарантии, их пределы и критерии принятия новых возможностей. [Методика разработки](docs/contract-development.md) объясняет, как применять их без лишней церемонии.

## Минимальное подключение

Начните с наблюдения за несколькими важными ограничениями. Явно выберите `advisory`: сейчас `init` по умолчанию создаёт блокирующую конфигурацию. Не включайте все возможности ради полноты.

Требуется `Node.js` 20+ по метаданным пакета; основной собственный CI проверяет версию 24. Закрепите проверенный экземпляр инструмента и укажите корень **репозитория-потребителя**, а не рабочую копию инструмента:

```bash
export REPO_GUARD_SHA=<40-char-SHA>
export CONSUMER_ROOT=/absolute/path/to/consumer
git clone https://github.com/netkeep80/repo-guard.git
cd repo-guard
git checkout "$REPO_GUARD_SHA"
npm ci
node dist/repo-guard.mjs --repo-root "$CONSUMER_ROOT" init --action-ref "$REPO_GUARD_SHA" --preset application --mode advisory
node dist/repo-guard.mjs --repo-root "$CONSUMER_ROOT" doctor
```

`REPO_GUARD_SHA` — полный 40-символьный SHA коммита. После официального выпуска допустим соответствующий тег `vX.Y.Z`. `init` не подставляет `main` или `latest`; требуется явный `--action-ref`. Проверка формы ссылки при генерации не доказывает принятие указанного коммита.

`init` создаёт четыре файла без перезаписи существующих: `repo-policy.json`, рабочий процесс проверки, шаблон PR и шаблон задачи. Просмотрите предложенные бюджеты и пути. `doctor` показывает фактический режим из политики и, когда может определить репозиторий и ветку `GitHub` и выполнить только чтение через `gh api`, отдельно сообщает `merge-barrier-coverage`: защищена ли ветка и какие обязательные статусы с привязкой к приложению наблюдаются. Он не меняет настройки `GitHub` и не подменяет свидетельство успешного выполнения конкретного статуса на конкретном `HEAD`; если репозиторий, ветка или `API` недоступны, покрытие остаётся явно непроверенным.

### Среда исполнения и транзитивные полномочия

`Node.js >=20` проверяется пакетным тестом на версии 20; основной конвейер проверки использует версию 24. Точная ссылка `repo-guard@<SHA>` закрепляет вложенный `setup-node`; доверенные пути проверки и выпуска закрепляют критичные `Actions`. Обычная проверка и публикация сайта не считаются независимым источником доверенных полномочий.

Для внешнего действия используйте точную принятую ссылку:

```yaml
- uses: netkeep80/repo-guard@<40-char-SHA>
```

В режиме `advisory` нарушения отражаются в отчёте без блокирующего кода выхода; ошибки загрузки или исполнения могут завершить команду с ошибкой. Включайте `blocking` для обоснованных границ после положительного и отрицательного свидетеля и настройки обязательной проверки.

## Рост вместе с проектом

| Потребность | Достаточный процесс |
| --- | --- |
| Небольшое изменение | Задача, ограниченное намерение, реализация, предметные тесты, ревью |
| Защита правил | Доверенная базовая политика, отдельная санкция, независимая обязательная проверка |
| Изменение поведения | Проверяемое ожидание, кандидат, положительный и отрицательный свидетель, явное принятие |
| Несколько версий и потребителей | Принятый контракт отдельно от кандидата, точные зависимости и воспроизводимое происхождение |

Успех тестов не превращает кандидата в принятую семантику. Если необходимой возможности нет в принятом внешнем контракте, честный результат — зафиксированный пробел и остановка на этой границе. Новый контракт не требуется для каждого исправления.

## Основные понятия

- `ChangeIntent`: `scope`, `must_not_touch` и дополнительные ограничения изменения. `must_touch` сейчас требует хотя бы одно совпадение из списка. `expected_effects` — описание для ревью, не доказательство эффекта.
- `GovernanceGrant`: отдельный блок `repo-guard-grant` только в теле однозначно связанной доверенной задачи. Ссылки `Part of #N`, `Fixes #N`, `Closes #N`, `Resolves #N` поддерживаются; комментарий не заменяет тело задачи. [Схема санкции](schemas/governance-grant.schema.json).
- Доверенные потолки политики не расширяются бюджетом намерения. Политика из PR не может самостоятельно отменить запрет базовой политики.
- `paths.pr_immutable`: запрет изменения, удаления и переименования защищённого пути через PR; санкция его не отменяет. Сам набор также нельзя менять через PR. Первичное включение требует отдельного доверенного процесса вне `check-pr`.
- Отношения документов проверяют объявленные значения и связи. Пакеты политики сводятся к этим обычным ограничениям; они не исполняют предметные доказательства вместо CI.

Точные гарантии зависят от конфигурации. Известные ограничения, включая старый путь при переименовании в `scope` / `must_not_touch`, перечислены в [требованиях продукта](docs/product-requirements.md#границы-текущей-реализации).

## Команды и справочники

| Команда | Назначение |
| --- | --- |
| `validate [change-intent.json]` | Проверить состояние и политику |
| `check-diff --base main --head feature` | Проверить локальное изменение |
| `check-pr --format json` | Получить решение и машинный отчёт в контексте PR |
| `init --action-ref <ref>` | Создать начальную конфигурацию |
| `doctor` | Проверить операционные предпосылки |

Канонические примеры — [`examples/scenarios/`](examples/scenarios/); формы публичных данных — [`schemas/`](schemas/). Небольшое ядро использует `FactRef`, `Constraint Program` и `primitive_relation`; [архитектура через границы доверия](docs/product-requirements.md#архитектура-и-владение-проверками) объясняет, зачем они нужны.

Снимок в [Обсерватории политики](https://netkeep80.github.io/repo-guard/) — производная проекция с временем наблюдения, а не самостоятельная authority принятия. Точные правила выпуска находятся в [`RELEASING.md`](RELEASING.md); версия пакета, принятый коммит и опубликованный выпуск различаются.

# repo-guard — локальный causal compiler для репозитория

README является производным пользовательским представлением. Нормативная authority находится только в канонических Requirements; порядок, примеры и поясняющий текст принадлежат project-owned document model.

```text
Snapshot
+ SubjectRef
+ Requirement
+ Relation
+ Constraint
+ Projection
```

## Канонические требования

Текст ниже берётся из поля `normative` канонических Requirement-файлов. README не является вторым нормативным источником.

### RG-01 — Независимая проверка принятого состояния

**`MUST`:** семантический verdict для изменения вычисляется детерминированно по точным `BASE/HEAD` и версионированным требованиям, отношениям, ограничениям и проекциям принятого снимка. Изменяемое описание PR, связанная задача, внешний сервис или секрет не должны менять результат для тех же входных снимков.

Риск — кандидат подменяет критерии собственной проверки или результат зависит от невоспроизводимого внешнего состояния. Нарушение — одинаковые `BASE/HEAD` дают разный семантический результат без изменения версионированных входов.

Средства: локальный compiler-only runtime, независимый BASE-owned compiler gate, обычный CI/CD и платформенные права review/merge.

### RG-02 — Принятие не выводится из готовности

**`MUST`:** если проект различает кандидата, принятое, текущее или опубликованное состояние, эти факты задаются явно и не выводятся автоматически из зелёного CI, merge, закрытой задачи или номера версии.

Риск — исследовательский или технически готовый кандидат незаметно становится предметной authority. Нарушение — consumer выбирает новое состояние только потому, что код собрался или был слит.

Средства: версионированные lifecycle-факты и отношения точных снимков; предметное принятие остаётся решением владельца и не подменяется компилятором.

### RG-03 — Ограниченная причинная область изменения

**`MUST`:** изменённый tracked Resource обосновывается явной причинной цепочкой от rooted Requirement; связь или Constraint одного Requirement не распространяется на несвязанный Resource. Requirement-scoped Constraint измеряет только область, выбранную его объявленными отношениями.

Риск — соседний или переименованный Resource проходит проверку без собственного причинного основания либо локальное ограничение превращается в скрытый глобальный барьер. Нарушение — orphan Resource считается допустимым только из-за близости пути, общего каталога или несвязанного изменения.

Средства: точная Git identity, J1 resource closure, J3 transition cause и relation-scoped Constraints.

### RG-04 — Свидетельство соответствует утверждению

**`MUST`:** результат сообщает точную identity входов, проверенное ограничение, наблюдение и предел вывода. Отсутствующее обязательное свидетельство нельзя называть успехом. `verified_by` задаёт traceability к проверочной поверхности, но не подменяет фактическое исполнение предметного теста или доказательства обычным CI. **`SHOULD`:** существенная гарантия имеет положительный и отрицательный свидетель.

Риск — зелёный цвет, наличие тестового файла или соседнее изменение выдаются за доказательство поведения. Нарушение — заявленная гарантия шире реально проверенного предиката.

### RG-05 — Воспроизводимое происхождение authority

**`MUST`:** если утверждение зависит от внешней семантики или артефакта, оно указывает именно проверенную принятую идентичность; кандидат и плавающая ссылка не выдаются за точный принятый источник. Разные authority фиксируются независимо. Осознанный выбор плавающей зависимости должен быть явным.

Риск — проверено одно, исполнено или принято другое. Нарушение — одного имени версии достаточно для заявления о совпадении контракта, исходников и артефакта. Машинно проверяются точные коммиты, значения контрактов, хеши и доступная история происхождения; это не автоматическое доказательство воспроизводимой сборки.

Средства: отношения документов и внешние проверки зависимостей/артефактов. В `aprover` обычный CI материализует точный `@mts/core` и проверяет пакет; в `anum_parser` отдельны семантическая и визуальная фиксации. Выпуск самого инструмента связывает точный принятый коммит с тегом и объектом выпуска.

### RG-06 — Явное подключение и честный охват

**`MUST`:** consumer явно выбирает неизменяемую версию RepoGuard и точные `BASE/HEAD`; отсутствие необходимых Requirements, Relations, предметного CI или платформенного required check нельзя выдавать за установленную защиту. **`SHOULD`:** первое полезное подключение моделирует только реально нужную причинную границу и не требует искусственной конфигурации.

Риск — процессный барьер без пользы или ложное ощущение защищённости. Нарушение — инструмент обещает merge protection или предметную корректность, которых фактически не наблюдает.

Средства: тонкий CLI/Action поверх `check`, обычный CI и настройки защиты ветки платформы.

### RG-07 — Свобода реализации и правильный владелец проверки

**`MUST`:** продукт ограничивает наблюдаемый результат и полномочия, не навязывает последовательность программирования. Проверку, которую лучше выполняют платформа, компилятор или предметный CI, не следует дублировать более слабым блокирующим аналогом без независимой ценности.

Риск — историческая форма реализации и ручная церемония становятся целью. Нарушение — корректное изменение отклоняется только из-за необоснованного числа файлов, формы теста или порядка работы. Проверяемы конкретные дублирующие пути исполнения; оценка независимой ценности остаётся архитектурным решением.

Средства: небольшие декларативные границы, внешние предметные свидетельства, факультативные бюджеты и подсказки. В `anum_parser` тест постоянного числа узлов сохранял дефект визуализации; правильный контракт разрешил изменить реализацию. В `aprover` честный `GAP` предпочтительнее локального обхода отсутствующей upstream-возможности.

### RG-08 — Самоупрощение вместо накопления возможностей

**`MUST`:** новая блокирующая возможность или публичное понятие обосновывается требованием `RG-*`, реальным неудовлетворённым случаем, независимой ценностью и сравнением с более простым решением. Равная гарантия при меньшей суммарной стоимости предпочтительна. **`SHOULD`:** удалять лишнее, переиспользовать и сводить удобства к существующему ядру до добавления семантики.

Риск — продукт становится процессным надзирателем. Нарушение — задача принимается только потому, что проверка локально полезна, увеличивает покрытие самоприменением или уменьшает одну метрику ценой новых понятий. Автоматизировать можно измерения; решение о необходимости не заменяется числом строк.

Средства: [единый план #518](https://github.com/netkeep80/repo-guard/issues/518), шаблон обоснования в методике, реальные внешние контрпримеры, измерения стоимости. Отсутствие нового свидетельства — достаточное основание не реализовывать предложение. Удаление возможности является полноценным улучшением.

### RG-09 — Явная и согласованная лицензия дистрибутива

**`MUST`:** распространяемый пакет RepoGuard явно декларирует принятую лицензию и включает соответствующий текст лицензии; package metadata и `LICENSE` не должны расходиться.

Риск — consumer получает неоднозначные или противоречивые условия использования. Нарушение — опубликованный пакет объявляет другую лицензию, не включает принятый license text или metadata и license artifact расходятся.

Средства: versioned package metadata, tracked `LICENSE` и executable consistency witness.

## Команды

### `build`

Без сетевых вызовов материализует только явно принадлежащие Projection файлы и области; Requirement relation сама по себе не даёт write authority.

```bash
repo-guard build --base <sha> --head <sha> --outputs outputs.json
```

### `check`

Локально проверяет exact `BASE/HEAD`, Requirements, Relations, Constraints и Projection freshness/ownership без записи.

```bash
repo-guard check --base <40-char-sha> --head <40-char-sha>
```

## Action

Для GitHub Actions закрепляйте принятую версию RepoGuard immutable SHA:

```yaml
- uses: netkeep80/repo-guard@<40-char-SHA>
  with:
    base: ${{ github.event.pull_request.base.sha }}
    head: ${{ github.event.pull_request.head.sha }}
```

## Материализация Projection

`build` применяет только bytes для явно объявленных Projection writers.

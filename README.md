# repo-guard — исполняемая политика репозитория

`repo-guard` проверяет не только итоговое состояние проекта, но и **форму изменения**: какие файлы затронуты, насколько выросли поверхности, выполнены ли обязательные сопутствующие изменения и не ослабляет ли изменение собственные правила проверки.

Инструмент предназначен прежде всего для длительной разработки с участием людей и ИИ, где локально удобные добавления постепенно создают архитектурный дрейф. Политика позволяет сделать ограничения на такой рост исполняемыми в CI.

## Архитектура

После программы архитектурного сжатия движок имеет один основной путь анализа:

```text
Git / GitHub / filesystem
          ↓
RepositoryFacts + DocumentFacts
          ↓
policy / contract / profiles
          ↓
named selectors + Constraint IR
          ↓
constraint kernel + specialized checks
          ↓
AnalysisReport
          ↓
text / json / summary
```

`RepositoryFacts` один раз нормализует изменение, набор отслеживаемых файлов, классификацию и чтение содержимого. `DocumentFacts` даёт общий разбор `Markdown`, `JSON` и `YAML` для контрактов, интеграции, реестров, трассировки и проверок текста.

`surfaces`, `new_file_classes`, ограничения путей и сопутствующих изменений используют один внутренний механизм именованных множеств. Базовые ограничения компилируются во внутренний `Constraint IR`, а не реализуются отдельным новым движком для каждого поля политики.

Доверие отделено от обычного ядра правил. Проверка PR использует политику текущей базовой ветки, поэтому PR не может сначала ослабить правила, которыми сам же проверяется. Сравнение политики выполняется через частичный порядок строгости; неизвестное изменение семантики считается `incomparable` и требует явной управляющей авторизации.

## Установка

Требуется `Node.js` 20 или новее. Для проверки PR также нужны `git`, `gh` и полная история репозитория.

```bash
npm install -g repo-guard
# либо
npx repo-guard
```

Для разработки самого проекта:

```bash
npm ci
npm test
node src/repo-guard.mjs
```

## Быстрый старт

```bash
repo-guard init --preset application --mode advisory
repo-guard doctor
```

Команда `init` создаёт, не перезаписывая существующие файлы:

- `repo-policy.json`;
- `.github/workflows/repo-guard.yml`;
- `.github/PULL_REQUEST_TEMPLATE.md`;
- `.github/ISSUE_TEMPLATE/change-contract.yml`.

Сгенерированный рабочий процесс закрепляет действие за версией выпуска, а не за изменяемой веткой.

## Команды

| Команда | Назначение |
| --- | --- |
| `repo-guard` | проверить и скомпилировать политику |
| `repo-guard path/to/contract.json` | проверить политику и контракт из файла |
| `repo-guard check-diff` | проверить локальное изменение |
| `repo-guard check-diff --base main --head feature` | проверить диапазон ссылок Git |
| `repo-guard check-pr` | проверить PR в CI |
| `repo-guard init` | создать начальную конфигурацию |
| `repo-guard doctor` | проверить окружение и подключение |
| `repo-guard validate-integration` | проверить декларативный слой `integration` |

Общие параметры можно указывать до или после команды:

```bash
repo-guard --repo-root /path/to/repo check-diff
repo-guard --enforcement advisory check-pr
repo-guard --enforcement blocking check-diff --base main --head feature
```

В режиме `blocking` нарушение даёт ненулевой код выхода. В режиме `advisory` нарушение остаётся в отчёте, но не ломает задание CI.

## Минимальная политика

```json
{
  "policy_format_version": "0.3.0",
  "repository_kind": "tooling",
  "enforcement": { "mode": "blocking" },
  "paths": {
    "forbidden": ["*.bak", "*.log"],
    "canonical_docs": ["README.md"],
    "governance_paths": ["repo-policy.json"],
    "operational_paths": []
  },
  "diff_rules": {
    "max_new_docs": 2,
    "max_new_files": 15,
    "max_net_added_lines": 1000
  },
  "content_rules": [],
  "cochange_rules": []
}
```

Основные высокоуровневые возможности:

- `diff_rules` ограничивает новые файлы, документы и чистый рост строк;
- `size_rules` ограничивает абсолютный размер и рост выбранных поверхностей;
- `surfaces` и `new_file_classes` именуют области для профилей изменений;
- `change_profiles` задаёт допустимую форму изменения по `change_type`;
- `content_rules` проверяет добавленный текст и язык документов;
- `cochange_rules` требует сопутствующие изменения;
- `registry_rules` сверяет канонические списки;
- `anchors` и `trace_rules` обеспечивают трассировку;
- `integration` проверяет подключение рабочих процессов, шаблонов и документации.

Это внешнее представление политики. Внутри движка несколько таких конструкций сворачиваются в общие селекторы и ограничения, поэтому новая возможность не обязана создавать новое семейство исполнения.

## Контракт изменения

Предпочтительная форма контракта в PR и задачах:

```repo-guard-yaml
change_type: refactor
scope:
  - src/**
budgets:
  max_new_files: 0
  max_new_docs: 0
  max_net_added_lines: 0
anchors:
  affects: []
  implements: []
  verifies: []
must_touch:
  - src/**
must_not_touch:
  - schemas/**
expected_effects:
  - реализация становится компактнее без изменения поведения
```

Ключевые поля — `change_type`, `scope`, `budgets`, `must_touch`, `must_not_touch`, `expected_effects` и `anchors.affects`. Поля `anchors.implements` и `anchors.verifies` связывают реализацию и проверку с трассируемыми якорями.

`check-pr` сначала ищет контракт в теле PR. Если его нет и PR однозначно связывает ровно одну задачу через `Fixes #N`, `Closes #N` или `Resolves #N`, контракт может быть прочитан из этой задачи.

## Контроль сжатия

`size_rules.max_growth` задаёт допустимое изменение размера поверхности относительно базы:

```json
{
  "id": "refactor-source-no-growth",
  "scope": "directory",
  "metric": "lines",
  "glob": "src/**",
  "max": 10000,
  "max_growth": 0,
  "applies_to_change_types": ["refactor"]
}
```

Ноль запрещает рост, отрицательное значение требует сжатия, положительное разрешает ограниченный рост. Сам `repo-guard` использует такой запрет для `src/**` и `schemas/**`, а профиль `refactor` дополнительно запрещает положительный чистый рост строк.

Архитектурные метрики доступны отдельной командой разработки:

```bash
npm run compression:metrics
npm run compression:metrics -- --compare <base-sha>
```

Цель метрики — не минимальное число строк любой ценой, а уменьшение числа специальных механизмов и мест, которые приходится синхронно менять для одной новой возможности.

## Доверенная политика и управляющие изменения

Пути из `paths.governance_paths` нельзя менять только потому, что текущий PR объявил такое намерение. Для их изменения связанная задача должна содержать `authorized_governance_paths`, а источник авторизации должен быть доверенным.

Версия `repo-policy.json` из PR валидируется как предполагаемое будущее состояние, но сам PR проверяется правилами базовой ветки. Это закрывает самоослабление политики в одном изменении.

При сравнении политики движок различает усиление, равенство, ослабление и несравнимое изменение. Ослабление и несравнимая управляющая семантика требуют отдельного управляющего изменения и явного `allow_policy_relaxation` в связанной задаче.

Если доверенную базовую политику получить нельзя, проверка завершается ошибкой, а не переходит на изменяемую политику из PR.

## Профиль requirements-strict

Встроенный профиль `requirements-strict` предназначен для проектов, где файлы требований в `JSON` являются каноническими якорями трассировки.

Профиль разворачивается в обычные `anchors` и `trace_rules`, а не создаёт второй движок. Подробности находятся в [`docs/requirements-strict-profile.md`](docs/requirements-strict-profile.md).

## Интеграционный слой

Секция `integration` описывает ожидаемое подключение инструмента: рабочие процессы, шаблоны PR и задач, документацию и профили.

```bash
repo-guard validate-integration
repo-guard validate-integration --format json
repo-guard doctor --integration --format summary
```

Переход с собственных валидаторов описан в [`docs/removing-bespoke-validators.md`](docs/removing-bespoke-validators.md). После доказанной эквивалентности старый валидатор следует удалить, а не оставлять вторым источником правил.

## Структурированный результат

Проверки используют общий `AnalysisReport`. Основные поля машинного результата: `command`, `mode`, `result`, `ok`, `exitCode`, `ruleResults`, `violations`, `advisoryWarnings`, `hints` и `repositoryRoot`.

Поддерживаются форматы `text`, `json` и `summary`.

## Самопроверка

Репозиторий применяет собственную политику к самому себе. Профиль подключения называется `self-hosting`.

Нормальный список возможностей не дублируется вручную: команды выводятся из реестра команд, правила — из реестра семейств, профили — из реестра профилей, а тесты автоматически обнаруживаются `tests/run.mjs`.

Файл [`docs/self-hosting-coverage.md`](docs/self-hosting-coverage.md) описывает эту модель. Машинный файл рядом хранит только честные исключения, которые невозможно содержательно применить к самому инструментальному репозиторию.

## Разработка и выпуск

```bash
npm ci
npm test
npm run compression:metrics
```

Порядок выпуска описан в [`RELEASING.md`](RELEASING.md). Общая роль проекта в портфеле — в [`PORTFOLIO.md`](PORTFOLIO.md), а межрепозиторные приоритеты находятся в `netkeep80/roadmap`.

`repo-guard` не заменяет предметные тесты, проверку безопасности или инженерное ревью. Его задача — сделать структурные ограничения изменения репозитория воспроизводимыми и исполняемыми.

# repo-guard — CI проверяет код, repo-guard проверяет границы изменения

**Уже есть хороший CI? Отлично: repo-guard нужен не вместо него.**

Обычный CI отвечает: **«кандидат собирается и проходит предметные проверки?»**  
`repo-guard` добавляет: **«имел ли этот PR право менять именно это, по каким принятым правилам он проверяется и не изменил ли кандидат критерии собственной приёмки?»**

| Обычный CI | repo-guard |
| --- | --- |
| Проверяет поведение программы | Проверяет допустимость самого изменения |
| Запускает тесты, сборку, линтеры | Проверяет `scope`, `authority`, связи и `evidence` |
| Показывает, что кандидат технически зелёный | Не даёт зелёному кандидату самому стать разрешением менять правила |

`repo-guard` особенно полезен при разработке с ИИ: агент может за один PR поменять код, тесты, документы и правила проверки. Инструмент оставляет реализацию свободной внутри явно разрешённых границ.

## Когда он реально полезен

- **ИИ исправил код и одновременно ослабил критерии приёмки.** Тесты могут остаться зелёными; защищённое правило без внешней санкции — нет.
- **Есть кандидат и принятое поведение.** Зелёный CI сам по себе не превращает новую семантику в принятую.
- **Требования версионируются.** Можно связать изменение требования с кодом, тестом и точной редакцией контракта.
- **Несколько представлений должны двигаться вместе.** Например, две реализации, контракт и `conformance`, версия и её зеркало.
- **PR должен быть хирургическим.** Разрешить одну поверхность, запретить соседнюю, ограничить новые файлы и рост `diff`.
- **Правила проекта не должны переписываться тем же PR.** Политика читается из доверенной базовой ветки, а изменение управления может требовать отдельный `GovernanceGrant`.

## Что конкретно умеет проверять

Функции включаются конфигурацией; использовать всё сразу не требуется.

| Проверка | Для чего |
| --- | --- |
| `scope`, `must_touch`, `must_not_touch` | Границы конкретного PR |
| `surfaces`, `change_profiles` | Разные разрешённые области для разных типов изменений |
| Бюджеты `diff` и размеров | Новые файлы, документы, строки и рост выбранных деревьев |
| `governance_paths` | Внешняя санкция на изменение правил управления |
| `pr_immutable` | Пути, которые PR менять не может вообще |
| `cochange_rules` | Обязательное совместное изменение связанных артефактов |
| Отношения документов | Равенство значений, `semver`-переходы, множества, ссылки и существование путей |
| Требования и `evidence` | Связь требований с реализацией и проверочными поверхностями |
| Версионирование | Один источник версии и согласованные зеркала |
| Контракт и `conformance` | Согласованная пара контракта, проверок и состояния принятия |
| Правила содержимого | Запрещённые шаблоны и текстовые соглашения |
| `doctor` | Наблюдаемая защита ветки и обязательные статусы |

Все эти проверки структурные. `repo-guard` не доказывает математическую, предметную или бизнес-корректность вместо вашего CI.

## Пример, который обычный CI не обязан ловить

PR от ИИ:

1. исправляет вычислитель;
2. обновляет тесты под новое поведение;
3. меняет документ доверенного основания;
4. объявляет результат готовым.

Код и новые тесты согласованы — CI зелёный.

При настроенном `repo-guard` реализация может оставаться разрешённой, а изменение доверенного основания — блокироваться, потому что оно входит в `governance_paths` и требует санкцию из связанной задачи. Сам PR не может выдать её себе.

То есть хороший CI и repo-guard решают разные задачи.

## Когда repo-guard не нужен

Не подключайте его ради галочки. Обычного CI и защиты ветки часто достаточно, если репозиторий мал, все изменения контролирует один человек, нет отдельной `authority` требований и контрактов, а ошибка в области изменения не несёт отдельного риска.

Начинайте с одной доказанной проблемы и режима `advisory`. Если проверка не защищает реальный риск, её не нужно включать.

## Минимальное подключение

Требуется `Node.js` 20+. Для первого запуска закрепите точную версию инструмента и включите наблюдение без блокировки:

```bash
export REPO_GUARD_SHA=<40-char-SHA>
export CONSUMER_ROOT=/absolute/path/to/consumer
git clone https://github.com/netkeep80/repo-guard.git
cd repo-guard
git checkout "$REPO_GUARD_SHA"
npm ci
node dist/repo-guard.mjs --repo-root "$CONSUMER_ROOT" init --action-ref "$REPO_GUARD_SHA" --preset application --mode advisory
node dist/repo-guard.mjs --repo-root "$CONSUMER_ROOT" doctor
```

`REPO_GUARD_SHA` — полный 40-символьный SHA коммита. После официального выпуска допустим соответствующий неизменяемый тег. `init` не подставляет `main` или `latest`: `authority` выбирается явно.

Для внешнего действия используйте принятую ссылку:

```yaml
- uses: netkeep80/repo-guard@<40-char-SHA>
```

`init` создаёт без перезаписи `repo-policy.json`, рабочий процесс проверки, шаблон PR и шаблон задачи. Базовая установка не настраивает защиту ветки и не создаёт независимый доверенный статус; полный контур описан в [руководстве](docs/trusted-deployment.md).

Режим `advisory` сообщает нарушения без блокирующего кода выхода. Переходите к `blocking` только после положительного и отрицательного свидетеля.

## Модель доверия

`ChangeIntent` описывает намерение PR: `scope`, ограничения и ожидаемый эффект. Намерение не является разрешением.

`GovernanceGrant` — отдельная санкция из тела однозначно связанной задачи. При проверке PR правила берутся из `trusted BASE` — доверенной базовой ветки, поэтому кандидат не может расширить себе полномочия собственной политикой.

Для реального барьера слияния одного успешного рабочего процесса недостаточно: нужен обязательный статус от доверенного производителя, защита ветки и разделение прав предлагающего изменение и разрешающего его.

`paths.pr_immutable` запрещает изменение выбранных путей через PR независимо от санкции. Пути управления требуют внешнее разрешение по принятой политике.

[Требования продукта](docs/product-requirements.md) определяют точные гарантии и их границы. [Методика разработки](docs/contract-development.md) описывает применение без лишней церемонии.

## Команды

| Команда | Назначение |
| --- | --- |
| `validate [change-intent.json]` | Проверить состояние и политику |
| `check-diff --base main --head feature` | Проверить локальный `diff` |
| `check-pr --format json` | Получить решение и машинный отчёт для PR |
| `init --action-ref <ref>` | Создать начальную конфигурацию |
| `doctor` | Проверить операционные предпосылки |

Канонические примеры находятся в [`examples/scenarios/`](examples/scenarios/), публичные формы данных — в [`schemas/`](schemas/).

Внутреннее ядро использует `FactRef`, `Constraint Program` и `primitive_relation`: высокоуровневые политики сводятся к небольшому набору конечных отношений, а не к растущему числу специальных проверяющих движков.

Снимок в [Обсерватории политики](https://netkeep80.github.io/repo-guard/) — производная проекция с временем наблюдения, не `authority` принятия. Правила выпуска находятся в [`RELEASING.md`](RELEASING.md).

## Разработка самого repo-guard

```bash
npm ci
npm run check:dist
npm test
npm run compression:metrics
```

Самоприменение: [`tests/test-c3-4b-self-host-exemplar.mjs`](tests/test-c3-4b-self-host-exemplar.mjs); исключения: [`docs/self-hosting-coverage.json`](docs/self-hosting-coverage.json).

Новая блокирующая возможность должна начинаться с реального контрпримера и требования продукта. Удаление лишней проверки — такое же улучшение, как добавление нужной. Единый план развития — [#518](https://github.com/netkeep80/repo-guard/issues/518).

# C3.2 — план реализации структурного сжатия

> Для исполнения используется навык `superpowers:executing-plans`. Разработка идёт через проверку сначала падающего, затем проходящего теста.

**Цель:** заменить квадратичное понижение `contract_conformance.cochange` на одну универсальную `cochange_group`, удалить обратное распознавание ролей из канонического ядра и сохранить независимые направленные `cochange_rules`.

**Спецификация:** `docs/superpowers/specs/2026-09-07-c3-2-structural-compression-design.md`.

## Ограничения

- `main` защищён; работа ведётся через задачу #373 и запрос изменений #389.
- После понижения `contract_conformance` не оставляет словаря предметных ролей в каноническом ядре.
- Для любого числа ролей создаётся ровно одна `cochange_group` и не создаются направленные производные рёбра.
- Независимые `cochange_rules` сохраняют существующую направленную семантику.
- Идентичность группы задаётся как `cochange-group:<id>`.
- Перестановка участников не меняет смысл группы.
- Изменение состава группы считается несравнимым изменением политики; удаление группы считается ослаблением.
- `cochange_group` выполняется на фазе перехода.
- Совместимость со старым внутренним представлением не сохраняется.

## Задача 1 — доказать новую структуру и поведение

Файлы:

- `tests/test-generated-cochange-identity.mjs`
- `tests/test-cochange-group.mjs`

Проверить:

- пять ролей понижаются в одну группу;
- `cochange_rules` не получают производных рёбер;
- в `src/checks/constraint-program.mts` отсутствуют предметные роли и функции обратного распознавания;
- ни один участник не изменён — проход;
- изменена непустая часть участников — нарушение;
- изменены все участники — проход.

Сначала зафиксировать падающий тест, затем минимальную реализацию.

## Задача 2 — публичная схема и смысловая проверка групп

Файлы:

- `schemas/repo-policy.schema.json`
- `src/policy-compiler.mts`
- `src/runtime/validation.mts`
- соответствующие тесты

Публичная форма:

```json
{
  "cochange_groups": [
    {
      "id": "example",
      "members": ["a.json", "b.json"]
    }
  ]
}
```

Схема обязана требовать:

- непустой `id`;
- не менее двух `members`;
- уникальные элементы `members`;
- отсутствие неизвестных полей.

Смысловая проверка обязана отвергать:

- повторяющиеся идентификаторы групп;
- некорректные пути репозитория;
- любые значения, которые обходят структурную проверку и доходят до внутреннего компилятора.

Проверка должна быть включена в общий путь загрузки политики, а неизвестные или некорректные группы должны завершаться отказом.

## Задача 3 — чистое понижение `contract_conformance`

Файл:

- `src/policy-profiles.mts`

Проверить:

- явная группа с `id = "contract-conformance"` конфликтует с автоматически создаваемой группой;
- квадратичный цикл генерации направленных правил удалён;
- автоматически создаётся одна группа с отсортированными путями;
- явные `cochange_rules` сохраняются без изменений.

## Задача 4 — каноническая программа ограничений

Файлы:

- `src/checks/constraint-program.mts`
- `src/checks/rules/constraints.mts`

Удалить:

```text
ContractConformanceRole
CochangeRoleEdge
CONTRACT_CONFORMANCE_DOCUMENT_ROLES
contractConformanceRolesByPath
cochangeRoleEdge
generatedContractConformanceCochange
```

Для каждой группы формировать одну запись с владельцем `cochange-group:<id>` и указателем `/cochange_groups/<id>`.

Смысл выполнения:

```text
changed(members) = ∅
или
changed(members) = members
```

Проверить сравнение политик:

```text
перестановка групп       -> равенство
перестановка участников  -> равенство
удаление группы          -> ослабление
изменение состава        -> несравнимость
добавление группы        -> усиление
```

## Задача 5 — метрики, документация и сборка

Файлы:

- `scripts/compression-metrics.mjs`
- `docs/architecture-compression-3-baseline.md`
- `README.md`, только если там перечислен публичный синтаксис
- сгенерированные файлы `dist/**`
- тест метрик C3.2

Машинно подтвердить:

```text
contract_conformance_role_vocabulary_in_canonical_core = 0
generated_edge_recognition_helpers = 0
contract_conformance_cochange_constraints = 1
macro_generated_positional_identity = 0
high_level_pack_semantic_edit_sites_in_canonical_core = 0
```

Документация должна объяснять разницу между:

- `cochange_groups` — все участники меняются вместе;
- `cochange_rules` — изменение одной стороны требует изменения хотя бы одной цели.

После изменения исходников выполнить штатную генерацию `dist` и потребовать зелёные проверки свежести сборки и полный набор тестов.

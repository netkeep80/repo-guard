# Полное доверенное развёртывание

Базовая команда `init` помогает начать пользоваться `repo-guard`, но намеренно не создаёт платформенную authority. Полный блокирующий контур появляется только тогда, когда независимый производитель статуса и защита ветки действительно не позволяют предложению изменения принять само себя.

Ниже описан путь для основной ветки `main`. Если у потребителя другая целевая ветка, все ограничения ветки и проверки workflow должны быть адаптированы и заново проверены как отдельная конфигурация.

## 1. Начните с наблюдения

Для первого подключения используйте точную принятую ссылку и явно выберите `advisory`:

```bash
repo-guard init --action-ref <40-char-SHA|vX.Y.Z> --preset application --mode advisory
repo-guard doctor
```

`init` создаёт четыре файла: политику, обычный рабочий процесс проверки, шаблон `PR` и шаблон задачи. Он не меняет настройки `GitHub`, не создаёт приложение и не включает защиту ветки.

Создаваемый рабочий процесс слушает `opened`, `synchronize`, `reopened` и `ready_for_review`. Это достаточный стартовый контур для наблюдения, но он не обеспечивает актуальность после изменения только тела `PR` или связанной задачи.

## 2. Докажите полезные границы

До перевода конкретного ограничения в `blocking` зафиксируйте положительный и отрицательный пример. Проверка должна различать именно требуемое поведение, а не удобную форму реализации.

После этого владелец проекта может изменить `repo-policy.json` на `blocking`. Само значение режима ещё не создаёт барьер слияния: пока платформа разрешает слияние без независимого обязательного статуса, это только блокирующий код выхода workflow.

## 3. Создайте независимого производителя статуса

Для той же модели authority, которую `repo-guard` использует при самоприменении, нужен отдельный `GitHub App`, установленный на репозиторий-потребитель.

Минимальное право приложения: запись `commit statuses`. Не выдавайте ему запись содержимого репозитория только ради этой проверки.

В репозитории создайте environment `trusted-enforcement` и сохраните:

- переменную репозитория `TRUSTED_ENFORCEMENT_APP_CLIENT_ID`;
- секрет окружения `TRUSTED_ENFORCEMENT_APP_PRIVATE_KEY`.

Приватный ключ не помещается в репозиторий и не передаётся PR.

## 4. Установите доверенный workflow

Возьмите `.github/workflows/trusted-enforcement.yml` из **той же точной версии `repo-guard`**, которой закреплён потребитель. Не копируйте файл с изменяемой ветки `main`.

В потребителе замените локальный вызов:

```yaml
uses: ./
```

на точную внешнюю ссылку:

```yaml
uses: netkeep80/repo-guard@<40-char-SHA>
```

После официального выпуска допустим соответствующий неизменяемый тег:

```yaml
uses: netkeep80/repo-guard@vX.Y.Z
```

Остальная топология существенна. Оценщик `PR` работает от `pull_request_target` для `opened`, `edited`, `synchronize`, `reopened`, `ready_for_review`; исполняемые правила доверия берутся из принятой ветки, а кандидат передаётся только как данные и `Git evidence`.

Отдельный обработчик `issues: edited` не выдаёт новый вердикт. Он находит только открытые готовые PR, которые **сейчас** ссылаются на изменённую задачу, и переводит их прежний `trusted-enforcement` в `pending`. Новый успех или отказ может опубликовать только обычный оценщик PR.

## 5. Сделайте статус реальным барьером

В защите ветки или `ruleset` для `main`:

1. запретите слияние без обязательных проверок;
2. добавьте `trusted-enforcement` как `required status check` и привяжите его к созданному `GitHub App`;
3. включите требование актуальности ветки перед слиянием, если `base drift` должен блокировать старые результаты;
4. добавьте предметные проверки проекта, которые действительно нужны для приёмки;
5. настройте запрет прямой записи в соответствии с моделью полномочий проекта.

Обычный статус с тем же именем, созданный другим приложением, не должен считаться эквивалентом доверенного производителя.

## 6. Проверьте фактическое покрытие

После настройки запустите:

```bash
repo-guard doctor
```

`merge-barrier-coverage` должен наблюдать защищённую целевую ветку и список обязательных проверок. Если GitHub возвращает привязку, `doctor` показывает её как `context@app:<id>`.

Это наблюдение только для чтения. `doctor` не выбирает правильный `app_id`, не меняет защиту ветки и не доказывает, что статус успешно выполнился на конкретном `HEAD`. Владелец должен сопоставить наблюдаемый идентификатор с установленным доверенным приложением.

## 7. Проверьте freshness отрицательными свидетелями

Перед объявлением полного блокирующего развёртывания воспроизведите минимум четыре случая:

| Изменение входа | Ожидаемое поведение |
| --- | --- |
| новый коммит в `PR` | новая обычная и доверенная оценка |
| изменение только тела готового PR | новая оценка по `edited` |
| изменение тела связанной задачи | старый доверенный статус становится `pending` |
| продвижение `main` | PR становится `behind`, если включена актуальность ветки |

После изменения связанной задачи `pending` — только инвалидация. Для свежего решения нужно обычное событие `PR`: например, изменение тела `PR`, новый коммит или другой поддерживаемый переход, который снова запускает оценщик.

## 8. Что считать достигнутой гарантией

Полный доверенный контур можно заявлять только одновременно при следующих условиях:

- политика содержит нужные границы и работает в `blocking`;
- доверенный рабочий процесс берётся из принятой версии;
- отдельный `GitHub App` является единственным ожидаемым производителем обязательного `trusted-enforcement`;
- ветка реально защищена и требует этот статус;
- freshness базы обеспечивается настройкой платформы;
- положительные и отрицательные свидетели воспроизведены на реальном репозитории.

Если какого-либо пункта нет, документируйте фактический уровень как `advisory` или частичный `blocking` и не обещайте независимую защиту слияния.

# Миграция на repo-guard v2.0.0

`v2.0.0` фиксирует новую несовместимую публичную границу `repo-guard`: чистую терминологию `ChangeIntent`, строгий исходный код на `TypeScript` и общий механизм управления контрактами и наборами проверок соответствия.

## Что изменилось несовместимо

### Намерение PR: `contract` → `ChangeIntent`

Сущность, описывающая намерение изменения PR, теперь называется только `ChangeIntent`.

- используйте блок `repo-guard-yaml` с полями `change_type`, `scope`, `budgets`, `anchors`, `must_touch`, `must_not_touch`, `expected_effects`;
- старые псевдонимы `contract` на уровне PR и прежняя форма языка удалены;
- термин `contract` освобождён для настоящих версионируемых машинных контрактов и контрактов выпуска проекта.

### Шаблон задачи

Старое имя шаблона `change-contract.*` заменено на `change-intent.*`.

`repo-guard init` создаёт `.github/ISSUE_TEMPLATE/change-intent.yml`.

### `GovernanceGrant` отделён от `ChangeIntent`

`ChangeIntent` не выдаёт PR управляющих разрешений. Изменение управляющих путей или разрешённое ослабление политики требует отдельного доверенного `GovernanceGrant`, прочитанного из связанной задачи.

PR не может авторизовать собственное ослабление политики.

## Граница исходного кода и поставки

Канонический редактируемый исполняемый код находится только в строгом `TypeScript` под `src/**/*.mts`.

`dist/**/*.mjs` — проверяемый сгенерированный результат сборки для пакета `npm` и действия `GitHub Actions`. Он должен воспроизводиться штатной сборкой и проходить `npm run check:dist`; каталог `dist` не является вторым деревом исходного кода.

## Управление контрактами и проверками соответствия

Вторая версия добавляет общий механизм, управляемый данными, без отдельного предметно-специфичного валидатора:

```text
DocumentFacts
  → exact JSON Pointer / typed scalar-set-path facts
  → generic document relations
  → Constraint Program
  → contract-conformance macro + evidence bindings
```

Механизм умеет выражать текущую и предыдущую пары контракта и проверок соответствия, указатели принятой версии, ссылки на пути репозитория, статическое покрытие блокирующим CI и соответствие смысловых идентификаторов доказательным якорям. Предметная семантика и фактическое выполнение тестов остаются обязанностью проекта и его CI.

Данные политики и контрактов не получают произвольного исполнения команд оболочки, обратных вызовов или подключаемого доступа к файловой системе и сети.

## Ссылка действия и закрепление версии

`repo-guard init` больше не выводит ссылку действия из версии пакета и не использует изменяемые `main` или `latest`.

Передавайте явно:

- полный 40-символьный идентификатор коммита; либо
- официальный тег `v2.0.0`, когда тег и выпуск GitHub уже опубликованы и совпадают с `package.json.version`.

До публикации официального выпуска используйте неизменяемый идентификатор принятого коммита.

Исторические закрепления потребителей за полными идентификаторами коммитов продолжают указывать на прежний код и не требуют слоя совместимости внутри второй версии. Миграция потребителя выполняется отдельно и осознанно.

## Проверка миграции

После смены закреплённой версии потребитель должен как минимум пройти собственный CI и блокирующую проверку `repo-guard`. Для внедрения управления контрактами и проверками соответствия рекомендуется сначала включить новую политику на принятой базе, затем отдельным PR удалить только те собственные проверки репозитория, для которых доказана положительная и отрицательная эквивалентность.

Специфичная для МТС или иная предметная семантика не переносится в `repo-guard` только ради удаления локальных тестов.

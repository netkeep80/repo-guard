# Откат параллельной миграции

Этот документ задаёт безопасный обратный путь для поэтапного включения параллельного режима repo-guard. Откат меняет только принадлежащие repo-guard служебные файлы и соответствующие внешние настройки. Прикладные контракты, исходный код проекта и его предметная семантика не откатываются.

## Предварительный просмотр

Перед любой записью сначала выполняется сухой прогон. Он классифицирует весь известный миграционный срез и ничего не изменяет.

```text
repo-guard migrate --parallel portable --action-ref <immutable-ref> --rollback --dry-run --format json
repo-guard migrate --parallel github_merge_queue --action-ref <immutable-ref> --rollback --dry-run --format json
```

Если хотя бы один существующий файл не совпадает с точным известным шаблоном, операция завершается отказом до первой записи. Пользовательские рабочие процессы не переписываются и не удаляются эвристически.

## Откат до внешнего принуждения

Если внешняя очередь или защита ветки ещё не включена, достаточно вернуть точные служебные файлы к прежнему режиму. Старый контроль запроса продолжает работать без изменения прикладной конфигурации.

```text
repo-guard migrate --parallel portable --action-ref <immutable-ref> --rollback --apply --format json
```

Для нативного поставщика команда имеет ту же форму.

```text
repo-guard migrate --parallel github_merge_queue --action-ref <immutable-ref> --rollback --apply --format json
```

Применение разрешено только после повторного чтения всего миграционного снимка. Любой дрейф между планированием и первой записью даёт отказ с нулём записей.

## Откат после внешнего принуждения

После включения внешних настроек порядок принципиален: сначала отменяется внешний параллельный контур, затем возвращаются файлы репозитория. Это исключает окно, в котором старые файлы уже восстановлены, а внешняя интеграция всё ещё считает параллельный протокол активным.

Для переносимого режима обратный порядок внешних шагов фиксирован:

```text
ready_label -> branch_protection
```

Сначала прекращается использование сигнала готовности, затем снимается только добавленная параллельным режимом часть защиты ветки. Не следует ослаблять независимые требования проекта.

Для нативного режима сначала отключается внешняя очередь:

```text
merge_queue
```

Только после этого выполняется файловый откат командой с `--rollback --apply`.

## Неизменяемая точка возврата

Предыдущая известная исправная версия может оставаться запасной точкой. Используется полный хеш фиксации либо официальный точный тег; изменяемые ссылки не являются допустимой точкой восстановления.

```text
allowed: 0123456789abcdef0123456789abcdef01234567
allowed: v2.0.0
forbidden: main
forbidden: latest
```

Возврат версии не требует отмены прикладных контрактов или изменений проекта, если они не зависели от параллельного режима.

## Совместимость и версия

Доказательства этапа P5 показывают добавочный характер нового пути: прежний режим остаётся вариантом по умолчанию, а параллельные возможности включаются явно. При сохранении этой совместимости целевая следующая версия — `v2.1.0`.

Сам P5d версию пакета не меняет, тег не создаёт и выпуск не публикует. Окончательный кандидат, самопроверка, пилотный потребитель и выпуск принадлежат этапу #311.

Мажорная версия нужна только если дальнейшая проверка докажет несовместимое изменение публичного контракта. Размер возможности сам по себе не является основанием для мажора.

# C3.10b — Consumer-policy compression через pure-lowering policy packs

Issue: #507  
Parent: #381  
Roadmap: #370  
External falsifier: `netkeep80/anum_parser#122`

## 1. Контекст и исходная цель

Architecture Compression 3.0 начиналась не как попытка построить ещё один язык политик. Исходный design input был двойным:

1. contract-driven discipline из `anum_docs`;
2. инженерные принципы, сформулированные в `andrej-karpathy-skills`:
   - Think Before Coding;
   - Simplicity First;
   - Surgical Changes;
   - Goal-Driven Execution.

Repo-guard должен переводить эти принципы в машинно-проверяемую дисциплину репозитория, но не содержать Karpathy-specific runtime или методологическую онтологию.

Целевой пользовательский поток:

```text
INTENT
что хотим получить
        ↓
SCOPE
что можно / нельзя менять
        ↓
LIMITS
насколько изменение может разрастись
        ↓
INVARIANTS
что обязано оставаться истинным
        ↓
EVIDENCE
чем доказано достижение цели
        ↓
canonical FactRef + finite relations
        ↓
ONE Constraint Program / evaluator
```

Главный критерий этого slice:

```text
complexity belongs in repo-guard lowering,
not in every consumer repo-policy.json
```

## 2. Что обнаружил внешний consumer

На accepted candidate:

```text
repo-guard = e5b9063c9d1c9e05404ec32b78ca005c278839ce
```

`anum_parser#122` попытался выразить простое правило:

```text
HEAD package.json:/version
    semver >
BASE package.json:/version
```

Ожидался RED на `0.5.0 > 0.5.0`.

Фактически policy compilation завершилась раньше:

```text
/document_relations/documents/base-package ...
/document_relations/documents/head-package ...
Proposed policy compilation failed
```

Причина:

- canonical `FactRef` уже содержит `snapshot = state | base | head` для document source;
- runtime reader уже умеет читать JSON/YAML/plain_text на BASE/HEAD;
- public schema `document_relation_document` разрешает `snapshot` только для `plain_text`.

Следовательно, public policy surface менее универсален, чем canonical core.

Второй симптом — authoring amplification. Для одного семантического намерения consumer должен вручную объявлять документы, snapshots, selectors и relations.

Это C3.10 architecture falsifier, а не повод создавать второй `VERSION` файл.

## 3. Наблюдение: packs уже частично существуют

Текущий source уже имеет внутренний registry `PACKS` для `requirements-strict`.

Одновременно `contract_conformance` реализован как отдельный high-level macro/lowering path.

Таким образом, сейчас существуют как минимум два разных public/high-level механизма:

```text
profile + profile_overrides
contract_conformance
```

при том что оба по архитектурной сути делают одно и то же:

```text
compact configuration
    -> deterministic expansion
    -> generic facts / relations / anchors / cochange
    -> canonical Constraint Program
```

Добавлять рядом третий механизм `macros` было бы архитектурным регрессом.

## 4. Решение: один closed built-in `packs` surface

Вводится одна публичная high-level конструкция:

```json
{
  "packs": {
    "<built-in-pack-name>": { }
  }
}
```

`packs` — закрытый registry встроенных шаблонов repo-guard.

Пользователь НЕ может:

- определять собственное тело pack;
- писать выражения;
- подключать JS/shell;
- задавать шаблонные строки, которые исполняются как DSL;
- регистрировать runtime plugins;
- добавлять relation primitive через policy.

Каждый pack имеет отдельную конечную JSON Schema конфигурации.

### 4.1. Pure lowering invariant

Любой pack обязан полностью исчезать до canonical evaluation:

```text
raw policy
  ↓ schema validation
packs registry
  ↓ deterministic lowering
expanded low-level policy
  ↓ canonical compiler
FactRef + finite relation descriptors
  ↓
Constraint Program
  ↓
evaluate / compare
```

После lowering runtime не знает, из pack пришёл constraint или был написан low-level policy вручную.

Обязательные нули:

```text
pack-specific runtime kinds = 0
pack-specific evaluators = 0
pack-specific comparison engine = 0
pack-specific FactRef types = 0
```

## 5. Никакой второй семантической authority

Low-level canonical policy остаётся семантической authority.

Pack является authoring sugar.

Это должно быть проверяемо эквивалентностью:

```text
lower(pack config) == explicit canonical policy
```

Для одинакового результата должны совпадать canonical constraint identities/shapes независимо от того, был ли intent выражен pack или вручную.

Следствие: замена explicit policy на семантически эквивалентный pack не должна создавать искусственную semantic policy delta после lowering.

## 6. Унификация существующих high-level mechanisms

До `v3.0.0` необходимо проверить возможность сведения существующих high-level механизмов к одному registry.

### 6.1. `requirements-strict`

Текущие:

```text
profile: requirements-strict
profile_overrides: ...
```

целевой вид:

```json
{
  "packs": {
    "requirements-strict": {
      "requirement_json_globs": ["..."],
      "evidence_surfaces": ["..."]
    }
  }
}
```

Default values остаются внутри built-in pack definition.

### 6.2. `contract-conformance`

Текущий отдельный top-level macro:

```text
contract_conformance
```

архитектурно должен рассматриваться как pack-кандидат:

```json
{
  "packs": {
    "contract-conformance": {
      "current": { },
      "previous": { },
      "acceptance": { }
    }
  }
}
```

Если в процессе реализации обнаружится доказанное свойство, из-за которого `contract_conformance` не может быть pure-lowering pack без усложнения canonical core, это является STOP condition и должно быть записано отдельным architecture decision.

До доказательства обратного отдельный public macro family не сохраняется только по исторической причине.

### 6.3. Legacy policy syntax

`v3.0.0` ещё не выпущен, поэтому постоянные aliases не нужны.

Если `profile/profile_overrides` и `contract_conformance` переводятся на `packs`, старые public формы удаляются в том же cutover.

Никакого dual-authority периода после acceptance slice.

## 7. Первый новый pack: `version-governance`

### 7.1. Пользовательский intent

```text
есть единственный version authority
каждый PR обязан увеличить semver относительно BASE
зеркала версии обязаны совпадать с HEAD authority
```

Целевой consumer config:

```json
{
  "packs": {
    "version-governance": {
      "authority": {
        "path": "package.json",
        "pointer": "/version"
      },
      "advance": "semver",
      "mirrors": [
        {
          "path": "package-lock.json",
          "pointer": "/version"
        }
      ]
    }
  }
}
```

Для `anum_parser` это сохраняет `package.json` единственной version authority, которую уже отображает Pages.

### 7.2. Lowering

Pack обязан lowering-ом получить эквивалент:

```text
FactRef A:
  document package.json
  snapshot=head
  pointer=/version
  type=string

FactRef B:
  document package.json
  snapshot=base
  pointer=/version
  type=string

relation:
  scalar_strictly_greater(A, B, comparator=semver)

FactRef C:
  document package-lock.json
  snapshot=head
  pointer=/version
  type=string

relation:
  scalar_equal(A, C)
```

Если mirror path изменяется отдельно от authority, существующий cochange primitive/rule может быть generated pack output, если это требуется для fail-closed поведения и не дублирует relation semantics.

### 7.3. Не входит в slice

`patch + 1` не добавляется.

Текущее универсальное семантическое требование:

```text
HEAD semver > BASE semver
```

Новый primitive допустим только по отдельному generic falsifier, а не ради этого consumer.

## 8. Второй новый pack: `repo-guard-workflow`

### 8.1. Пользовательский intent

Consumer должен иметь возможность сказать:

```text
repo-guard workflow является blocking gate
Action immutable pinned
mode = check-pr
permissions read-only
```

без ручного знания YAML pointers GitHub Actions.

Пример целевой конфигурации:

```json
{
  "packs": {
    "repo-guard-workflow": {
      "path": ".github/workflows/repo-guard.yml",
      "action": "netkeep80/repo-guard",
      "ref": "<exact accepted SHA>",
      "mode": "check-pr",
      "enforcement": "blocking",
      "permissions": {
        "contents": "read",
        "issues": "read",
        "pull-requests": "read"
      }
    }
  }
}
```

`ref` остаётся явным exact SHA. Pack не должен скрывать mutable ref.

### 8.2. Lowering

Pack разворачивается в обычный YAML document fact + `scalar_equals_literal` relations для:

- `uses` exact ref;
- `mode`;
- `enforcement`;
- required permissions.

Никакой GitHub-workflow-specific проверки после lowering не существует.

## 9. Document format и snapshot

### 9.1. Snapshot parity

Public low-level document definition больше не должен иметь plain-text-only special case.

Минимальный обязательный результат:

```text
json     supports state/base/head
yaml     supports state/base/head
plain    supports state/base/head
```

Это не новая runtime capability: canonical reader уже её имеет.

### 9.2. Format inference

Для pack document references формат определяется детерминированно:

```text
*.json -> json
*.yaml -> yaml
*.yml  -> yaml
```

Неоднозначный/extensionless path требует explicit format и fail-closed без него.

На этом slice не обязательно менять low-level `document_relations.documents` на inference, если pack surface уже скрывает boilerplate. Low-level expert surface может сохранять explicit format, если это уменьшает schema ambiguity.

## 10. Conflict model

Packs lower в тот же semantic namespace, что explicit policy.

Правила:

1. generated ids deterministic;
2. generated ids используют reserved prefix `pack:<pack-name>:`;
3. collision generated/generated — compile error;
4. collision generated/explicit id — compile error;
5. semantic contradiction между двумя constraints не разрешается порядком/precedence; оба constraints существуют и evaluation fail-closed, если одновременно невыполнимы;
6. explicit policy не может "override" pack незаметно.

Нет hidden precedence rules.

## 11. Registry design

Built-in pack registry должен содержать только metadata и lowering function/config, необходимые до canonical compiler.

Концептуально:

```text
PackDescriptor
  name
  config schema
  lower(config) -> PolicyFragment
  docs/scenario identity
```

`PolicyFragment` использует уже существующие public/canonical families:

- document relations;
- anchors;
- trace rules;
- cochange groups/rules;
- другие существующие lowerable policy fragments.

Pack descriptor не содержит evaluator callback.

Новый pack добавляется через один registry edit-site + schema/tests/scenario/docs.

## 12. Когда разрешено добавлять новый pack

Pack принимается только если выполнены все условия:

1. есть минимум два реальных повторения паттерна: разные consumers либо external consumer + self-host/scenario;
2. intent стабилен и понятен без знания конкретного проекта;
3. lowering полностью выражается текущим canonical core;
4. consumer authoring уменьшается измеримо;
5. pack не содержит methodology-specific vocabulary;
6. есть executable PASS + bounded FAIL scenario;
7. public docs объясняют intent, а не внутренний expansion boilerplate.

Если паттерн встретился один раз — использовать explicit policy.

## 13. Связь с Karpathy-inspired principles

Никакого `karpathy: true` pack не существует.

Принципы выражаются ортогональными универсальными возможностями:

| Principle | Repo-guard representation |
| --- | --- |
| Think Before Coding | ChangeIntent / declared scope / explicit assumptions in issue/PR boundary |
| Simplicity First | diff budgets / size no-growth / compact packs вместо repeated boilerplate |
| Surgical Changes | scope, must-touch, must-not-touch, surfaces, governance boundary |
| Goal-Driven Execution | invariants + executable evidence + RED→GREEN acceptance |

Таким образом repo-guard поддерживает подход, не становясь привязанным к Claude, Codex, Cursor или конкретному автору методологии.

## 14. Observability

Pack не должен становиться скрытой магией.

Минимально diagnostics должны уметь показать:

```text
pack name
pack config origin
сколько canonical constraints generated
relation ids, упавшие при evaluation
```

Pages Policy Observatory должен показывать связь:

```text
pack intent -> lowered canonical relations
```

без создания второй authority.

Отдельный новый evaluator/Pages logic для pack запрещён; observability строится из lowering result / AnalysisReport.

## 15. Testing strategy

### 15.1. Unit/schema

Проверить:

- unknown pack rejected;
- user-defined macro body rejected;
- invalid pack config rejected;
- deterministic generated IDs;
- conflicts fail-closed;
- JSON/YAML BASE/HEAD snapshots проходят public validation;
- ambiguous format fails closed.

### 15.2. Lowering equivalence

Для каждого pack иметь тест:

```text
compile(pack policy)
  canonical-equivalent-to
compile(explicit expanded policy)
```

Не требуется byte-identical raw policy; требуется одинаковая canonical semantic shape.

### 15.3. Executable scenarios

Обновить/добавить минимальные сценарии:

#### version-transition

Authority = structured `package.json`, а не synthetic plain-text `REVISION`.

Positive:

```text
0.5.0 -> 0.5.1
mirror == authority
```

Negative A:

```text
0.5.0 -> 0.5.0
```

должен упасть именно на semver greater relation.

Negative B:

```text
package.json=0.5.1
package-lock.json=0.5.0
```

должен упасть на equality relation.

#### repo-guard-workflow

Positive exact pin/blocking/read-only.

Bounded negatives для wrong pin или mutable ref, wrong mode/enforcement, writable permission.

## 17. Compression metrics

C3.10b не принимается по субъективному "стало красивее".

Измерить минимум:

```text
consumer repo-policy total lines / bytes
feature-local policy lines / fields
explicit document declarations
explicit selectors
explicit relation rules
high-level public concept count
pack count
canonical generated constraint count
runtime kinds
relation primitive kinds
core semantic edit-sites
pack-specific runtime edit-sites
```

Обязательный результат:

```text
consumer authoring complexity materially DOWN
public high-level concept count does not grow without deleting/merging older concepts
canonical runtime kinds remains 1
canonical relation algebra does not grow solely for packs
pack-specific runtime edit-sites = 0
```

Особенно важно: если добавление `packs` оставляет рядом `profile`, `profile_overrides`, отдельные macro families и не уменьшает public concept count, slice считается архитектурно подозрительным и требует пересмотра.

## 19. STOP conditions

Остановиться и пересмотреть дизайн, если реализация требует хотя бы одно:

- второй evaluator;
- arbitrary expression language;
- runtime branch по pack name;
- project-specific logic для `anum_parser`/`anum_docs`;
- сохранение одновременно старого и нового macro surface только ради compatibility;
- нового relation primitive, полезного только одному pack;
- hidden override/precedence semantics;
- macro expansion, которую невозможно отобразить как canonical constraints.

## 20. Definition of Done

- один built-in pack registry;
- no user-defined macro language;
- existing high-level macro/profile mechanisms либо сведены к registry, либо их отдельность доказана architecture decision;
- `version-governance` и `repo-guard-workflow` существуют как pure lowering;
- structured BASE/HEAD snapshots доступны без plain-text special case;
- pack vs explicit lowering equivalence доказана тестами;
- scenarios GREEN;
- self-host GREEN;
- docs/Pages показывают compact intent и lowered evidence;
- `anum_parser#122` даёт intended RED -> GREEN на exact accepted SHA;
- consumer policy metrics показывают реальное сжатие;
- canonical runtime/evaluator architecture не разрослась;
- `v3.0.0` остаётся HOLD до завершения #381.

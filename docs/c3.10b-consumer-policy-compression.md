# C3.10b — Сжатие пользовательской политики

Связанная задача: `#507`  
Родительская задача: `#381`  
Дорожная карта: `#370`  
Внешний фальсификатор: `netkeep80/anum_parser#122`

## 1. Исходная цель

Архитектурное сжатие версии 3.0 начиналось не как попытка создать ещё один язык политик.

Исходными ориентирами были дисциплина разработки через контракт и четыре инженерных принципа:

- сначала понимать изменение;
- выбирать самое простое достаточное решение;
- менять только необходимую область;
- формулировать проверяемый результат и доказательство его достижения.

Эти идеи должны выражаться машинно-проверяемыми ограничениями репозитория, но не отдельной методологической подсистемой.

Целевой пользовательский поток:

```text
намерение
  ↓
область изменения
  ↓
ограничения размера и роста
  ↓
инварианты
  ↓
доказательства
  ↓
FactRef + конечные отношения
  ↓
единая Constraint Program
  ↓
единый evaluator
```

Главный критерий текущего этапа:

```text
сложность должна находиться внутри lowering repo-guard,
а не повторяться в каждом repo-policy.json потребителя
```

## 2. Что обнаружил внешний потребитель

Принятый исходный кандидат:

```text
repo-guard = e5b9063c9d1c9e05404ec32b78ca005c278839ce
```

Потребитель попытался выразить простое правило:

```text
HEAD package.json:/version
    semver >
BASE package.json:/version
```

Ожидался отказ на сравнении неизменившейся версии:

```text
0.5.0 > 0.5.0 = false
```

Вместо этого проверка остановилась при компиляции политики.

Причина состоит в рассинхронизации публичного описания и канонического ядра:

- каноническая ссылка на факт уже различает состояние, базу и голову;
- чтение снимков уже работает для структурированных документов и обычного текста;
- публичная схема разрешала снимок только у обычного текста.

Следовательно, публичная политика была менее универсальной, чем само ядро.

Второй симптом — избыточность записи. Одно смысловое правило требовало вручную объявлять несколько документов, селекторов и отношений.

Это архитектурный фальсификатор этапа C3.10, а не причина заводить второй файл версии.

## 3. Первый обязательный cutover: снимок принадлежит селектору

Документ описывает идентичность источника:

```json
{
  "path": "package.json",
  "format": "json"
}
```

Снимок относится к конкретному чтению этого источника:

```json
{
  "document": "package",
  "snapshot": "head",
  "pointer": "/version",
  "type": "string"
}
```

Допустимые снимки:

```text
state
base
head
```

Одинаковая модель применяется к структурированным документам и обычному тексту.

Это не новая семантика. Публичный слой только приводится в соответствие с уже существующей канонической моделью факта.

## 4. Наблюдение о существующих высокоуровневых механизмах

В исходном коде уже существуют два разных способа компактной записи высокоуровневой политики.

Первый механизм обслуживает строгий профиль требований. Второй обслуживает связку контракта и соответствия.

Архитектурно оба делают одно и то же:

```text
компактная конфигурация
  ↓
детерминированное разворачивание
  ↓
обычные факты, отношения, якоря и совместные изменения
  ↓
каноническая программа ограничений
```

Добавление рядом третьего независимого механизма макросов увеличило бы число понятий и противоречило бы цели сжатия.

## 5. Решение: один закрытый набор встроенных пакетов

Публичная высокоуровневая поверхность должна быть единой:

```json
{
  "packs": {
    "<built-in-pack-name>": {}
  }
}
```

Пакет является только способом краткой записи намерения.

Его жизненный цикл:

```text
короткая конфигурация
  ↓
детерминированное lowering
  ↓
существующие FactRef
  ↓
существующие отношения
  ↓
существующая Constraint Program
  ↓
существующий evaluator
```

После разворачивания происхождение ограничения из пакета не имеет отдельной исполнительной семантики.

Жёсткие нули:

```text
pack-specific runtime kinds = 0
pack-specific evaluators = 0
pack-specific comparison engines = 0
pack-specific FactRef types = 0
```

## 6. Почему пакеты закрытые

Пользователь не может определять собственное тело макроса.

Запрещены:

- произвольные предикаты;
- пользовательский программный код внутри политики;
- выполнение команд из политики;
- шаблонизатор общего назначения;
- пользовательские плагины времени выполнения;
- произвольный язык выражений.

Иначе краткая политика быстро превратится в новый язык программирования, а у репозитория появится второй источник семантики.

Список пакетов конечный и принадлежит самому инструменту.

## 7. Условие появления нового пакета

Новый пакет допускается только при одновременном выполнении всех условий:

1. одно и то же намерение реально повторилось в нескольких репозиториях или исполняемых сценариях;
2. разворачивание полностью детерминировано;
3. результат выражается уже существующими фактами и отношениями;
4. пользовательская политика становится существенно короче и понятнее;
5. пакет не содержит знания о конкретном проекте или методологии;
6. существуют исполняемые положительный и отрицательный случаи.

Если хотя бы одно условие не выполнено, правило остаётся явным низкоуровневым описанием.

## 8. Первый новый пакет: управление версией

Назначение:

- один источник версии;
- каждый обычный запрос на слияние обязан повысить версию относительно базы;
- зеркала версии обязаны совпадать с текущим источником.

Целевая запись для парсера:

```json
{
  "packs": {
    "version-governance": {
      "authority": {
        "path": "package.json",
        "pointer": "/version"
      },
      "advance": "semver",
      "mirrors": [
        {
          "path": "package-lock.json",
          "pointer": "/version"
        }
      ]
    }
  }
}
```

Разворачивание обязано породить только существующие отношения:

```text
HEAD authority.version > BASE authority.version
HEAD authority.version = HEAD mirror.version
```

Сравнение версии использует семантический порядок.

Требование «ровно следующая исправительная версия» не вводится. Достаточно строгого увеличения версии.

Файл `package.json` остаётся единственным источником версии приложения.

## 9. Определение формата документа

Для ссылок внутри пакетов допустимо безопасное определение формата по расширению:

```text
.json       -> json
.yaml/.yml  -> yaml
```

Неоднозначный путь обязан явно задавать формат.

Такое определение сокращает запись, но не меняет семантику фактов.

## 10. Второй новый пакет: защита рабочего процесса repo-guard

Повторяющееся намерение потребителей:

- действие закреплено на неизменяемом точном коммите;
- режим проверки запроса на слияние включён;
- блокирующее применение обязательно;
- права токена только на чтение.

Целевая конфигурация:

```json
{
  "packs": {
    "repo-guard-workflow": {
      "path": ".github/workflows/repo-guard.yml",
      "action": "netkeep80/repo-guard",
      "ref": "<exact-sha>",
      "mode": "check-pr",
      "enforcement": "blocking",
      "permissions": {
        "contents": "read",
        "issues": "read",
        "pull-requests": "read"
      }
    }
  }
}
```

Пакет разворачивается в обычное чтение YAML и существующие сравнения скалярных значений.

Отдельной логики рабочего процесса в исполнительном ядре быть не должно.

## 11. Консолидация уже существующих механизмов

До выпуска версии 3.0 следует проверить возможность представить существующие высокоуровневые возможности через тот же реестр пакетов.

Кандидаты:

```text
requirements-strict
contract-conformance
```

Если их перенос требует только изменения высокоуровневого lowering, старые отдельные публичные формы удаляются.

Совместимые псевдонимы не сохраняются.

Если перенос неожиданно требует новой исполнительной семантики, работа останавливается и причина фиксируется как отдельное архитектурное решение. Нельзя проталкивать объединение ценой второго ядра.

## 12. Правила объединения результатов пакетов

Пакеты могут создавать документы, отношения, якоря и правила совместного изменения.

Идентификаторы, создаваемые автоматически, используют зарезервированное пространство:

```text
pack:<pack-name>:...
```

Коллизия двух автоматически созданных сущностей является ошибкой.

Коллизия автоматически созданной сущности с явной сущностью также является ошибкой.

Явная политика не получает скрытого приоритета над результатом пакета.

Таким образом исключается неявное переопределение семантики.

## 13. Отношение пакетов к низкоуровневой политике

Низкоуровневые факты и отношения остаются семантическим авторитетом.

Пакеты предназначены для повторяющихся намерений. Уникальное или редкое ограничение можно записать явно.

При этом один и тот же смысл не должен одновременно описываться пакетом и отдельным ручным набором отношений.

Исполняемая проверка обязана доказать эквивалентность компактного пакета и его канонического разворачивания.

## 14. Метрика сжатия

Успех не определяется одним зелёным запуском.

Для реального потребителя измеряются до и после:

- строки политики;
- байты политики;
- число объявлений документов;
- число вручную записанных селекторов;
- число вручную записанных отношений;
- число понятий, которые необходимо понимать автору политики;
- число канонических ограничений после разворачивания;
- число изменений исполнительного ядра ради пакета.

Требуемый результат:

```text
consumer authoring complexity: DOWN materially
canonical runtime complexity: unchanged
consumer-specific core logic: 0
```

## 15. Обязательные исполняемые доказательства

### Снимки документов

Структурированные документы и обычный текст обязаны одинаково поддерживать состояние, базу и голову через селектор.

### Управление версией

```text
BASE 0.5.0 -> HEAD 0.5.0 = FAIL
BASE 0.5.0 -> HEAD 0.5.1 = PASS
authority 0.5.1 != mirror 0.5.0 = FAIL
```

Основной сценарий версии должен использовать реальный структурированный источник, а не искусственный отдельный файл только ради удобства проверки.

### Защита рабочего процесса

Независимо должны обнаруживаться:

- неверная или изменяемая ссылка на действие;
- неверный режим;
- неблокирующее применение;
- право на запись вместо требуемого чтения.

### Эквивалентность lowering

Компактная конфигурация и её явное каноническое разворачивание обязаны приводить к эквивалентной программе ограничений.

## 16. Самоприменение

Сам `repo-guard` должен использовать пакет там, где это действительно сокращает его собственную политику.

Нельзя переводить одноразовое правило в пакет только ради демонстрации возможности.

Публичная страница должна показывать одновременно:

- компактное намерение;
- получившиеся канонические факты;
- получившиеся отношения;
- отсутствие отдельного исполнительного пути пакета.

Страница остаётся только наблюдаемой проекцией и ничего не изменяет в репозитории.

## 17. Внешнее доказательство на anum_parser

До принятия текущего этапа запрос `anum_parser#122` остаётся красным внешним фальсификатором.

Запрещены обходы через второй источник версии или специальный скрипт потребителя.

После принятия нового точного коммита repo-guard последовательность такая:

1. закрепить потребителя на новом точном коммите;
2. заменить подробное временное описание компактными пакетами;
3. сохранить версию `0.5.0` и получить отказ именно на её отсутствии роста;
4. повысить источник и зеркало до `0.5.1`;
5. получить зелёные проверки;
6. завершить уже одобренное сжатие времени CI;
7. слить точную проверенную голову;
8. проверить публикацию страницы с `v0.5.1` из `package.json`;
9. записать метрики политики и CI в `#381`.

## 19. Критерии принятия

Работа считается принятой только когда одновременно выполнено следующее:

- публичная модель снимков совпадает с канонической моделью фактов;
- существует один закрытый реестр встроенных пакетов;
- новые пакеты ограничены реально повторяющимися сценариями;
- управление версией полностью понижается в существующие факты и отношения;
- защита рабочего процесса полностью понижается в существующие факты и отношения;
- существующие высокоуровневые механизмы сведены к тому же реестру, если это не требует новой семантики;
- пользовательский язык макросов не появился;
- исполняемые сценарии доказывают положительные и отрицательные случаи;
- самоприменение, документация и публичная страница описывают одну модель;
- внешний потребитель получает требуемую последовательность отказа и успеха на точном принятом коммите;
- пользовательская политика становится измеримо проще;
- число исполнительных видов остаётся равным одному;
- специальная логика конкретного потребителя отсутствует;
- выпуск версии 3.0 остаётся заблокированным до завершения всех ворот задачи `#381`.
